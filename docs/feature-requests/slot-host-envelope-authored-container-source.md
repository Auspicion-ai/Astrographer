## 1. What this request asks, in three clauses

1. **A SUPPORTED CONTAINER SOURCE FOR ENVELOPE-AUTHORED CONSUMERS.** A documented, supported way for a consumer whose nodes are **authored as provident envelope DATA and materialised by the runtime** — rather than created by the caller as DOM elements — to satisfy `SlotHostOptions.containerFactory`'s obligation ("key → that key's container"), **or** an explicit statement that no such form is admissible and the slot host is caller-created-node-only by design.
2. **A CONFORMANCE-INCLUDABLE `slot-host` SUITE (OR A DECLARED ABSENCE).** Either a minimal-harness subset of the foundation's `slot-host.test.ts` that a consuming fork can supply and run, **or** an explicit declaration that no such subset exists and the mechanism cannot be evaluated in a consumer without importing foundation application context — so an adopting fork's conformance reading can be honest either way.
3. **A ONE-BLOCK CONTRACT CLARIFICATION OF THE CONTAINER SOURCE.** Beyond "offers `appendChild`": the element's **identity/lifecycle** expectations (may the same container be returned for two keys? may it be re-returned after a re-sync? must it survive a `null`→present parent transition?), and whether **`owned-list-host`'s `mount` + `itemFactory`** carry the **same** caller-created-node limitation (its own header says so, but the two must be answerable together for a consumer planning one integration).

## 2. The gap, stated exactly

Both vendored hosts declare themselves **for CALLER-CREATED nodes**, and both take their containers from injected sources:

- `slot-host.ts` header: *"A per-key container manager for **CALLER-CREATED nodes**. The caller declares the keys once; thereafter it supplies (key → node) pairs, an injected ordering policy, injected attribute/class policies **and the injected element factory its containers come FROM** … It authors no content of its own … every container is the value the INJECTED `containerFactory` returned for that key."*
- `SlotHostOptions.containerFactory` is documented as *"**The SOLE container source**: the caller's element factory, called once per declared key that needs a container. The value it returns IS that key's container"* — and its absent/non-callable/throwing/unusable answers degrade to *"every operation is a valid no-op with a valid state and **nothing is placeable**, with no container-state refusal."*
- `owned-list-host.ts` header: *"A container manager for **CALLER-CREATED nodes**"*, with `mount` documented as *"the container the host places CALLER-CREATED nodes inside"* and `itemFactory` only consulted *"when an entry supplies no node."*

**The fork's model is the other one, by its own project-wide constraint.** Every UI element that is not the Electron shell itself must be **rendered with the provident framework** — authored as envelope data and driven through the producing graph — so that it stays visible to `provident.dispatch` / `get_rendered_html` / `get_markdown`. The zone containers are therefore **authored as envelope data** (the fork's `pane-graph` authors the zone nodes), not created by a caller. There is consequently **no caller-created element to hand a factory**, and the fork's own measurement of the consequence is the boundary record's: **12 seam slots over the two hosts = 2 supplied + 1 supplied-but-incompatible + 9 `must be built`, with `containerFactory` the one named obstacle**, and `U-SLOTHOST`'s moved-half **EMPTY** (the fork has no admissible caller-created chrome-node set to hand a slot host).

- **It must not duplicate it.** Duplicating a mechanism is the exact condition this request exists to end: the fork's audit found the zone/gutter/gesture/relocate/layout-projection surface **locally reimplemented** while all eight corresponding modules were imported by nothing.
