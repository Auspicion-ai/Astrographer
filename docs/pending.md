# Astrographer — Pending / Parked / Speculative

Maintained by the document-archival loop (AGENTS.md item 6). Three kinds of
rows: (a) UPSTREAM — constraints owned by the `provident-ssr` project that this
project must respect (imported from `../Provident-Electron/docs/` and
`../Preempt-Providence/docs/`); (b) DEFERRED — lower-value gaps parked until a
use case surfaces; (c) SPECULATIVE — future features with their revisit
conditions.

Retired PARKED and SPECULATIVE rows are archived in the gitignored `archive/`
dir and do not ship in a fork (see `docs/FORKER.md` §1/§5).

## DEFERRED (lower-value / parked)

| Item | Date | Constraint / revisit condition |
| --- | --- | --- |
| **Vector embeddings** | 2026-08-26 | Deferred behind the interface-swappable `Embedder` (Unit F). Lexical-first (BM25/tf-idf) is the deterministic, offline MVP. Revisit when a local vector model is available or network egress is allowed. |
| **contenteditable rich inline editing** | 2026-08-26 | Rejected for v1 (fights graph-is-authoritative; `DomAdapter.text` clobbers a live editor). Form-control editing (commit-on-blur) is the v1 path. **Focused validity check 2026-08-26: FEASIBLE-WITH-CONSTRAINTS** — per-element graph-authority suspension is cleanly implementable via a `DomAdapter` decorator wrapper (skip `setProp(wire,'text',…)` for a `suspendedWires` set; forward `.wires`/`beginBatch`/`endBatch`); the write-back model (on blur → RAG store → re-traversal) is untouched; no engine gap. Constraints: (1) the suspension only intercepts `set` text ops — it does NOT prevent a full re-traversal from re-creating the edited element (the dirty-edit guard is the protection for that case); (2) HTML→plain-text conversion on blur is a real project-specific gap for rich subtrees (`ul`+`li`, `strong`, `em`) — the contenteditable produces HTML that must be decomposed back into the RAG store's per-node plain-text `content` + element `type` tree; (3) the current `CaretState` (`{ offset, focused }`) does not capture a rich contenteditable's Selection/Range. **If pursued later, scope to single-node plain-text editing (a `p`/leaf) where `textContent` conversion is trivial, and keep the textarea for rich subtrees.** The rich-subtree HTML→provident-tree converter is a SEPARATE feature request for an external importable package — `docs/feature-requests/rich-text-html-to-provident-tree.md`. Revisit when a caret-preserving in-provident editor becomes feasible. |
| **Stored document-flow edges as a separate engine mechanism** | 2026-08-26 | Rejected — doc-flow edges are authoritative in the RAG store; the traversal maps them to family order + a doc-head marker prop. No new engine roles (closed `Role` union). |

## SPECULATIVE (future features)

| Item | Date | Constraint / revisit condition |
| --- | --- | --- |
| **Markdown-vs-source diffing to detect changes** | 2026-08-26 | User decision: markdown is EXPORT-ONLY; agent changes go through direct MCP updates. Diffing markdown vs. generated source to detect changes is a FUTURE SPECULATIVE feature. Revisit when a use case needs change-detection from the export surface. |
| **Remote embedding provider** | 2026-08-26 | Deferred behind the `Embedder` interface. Requires network egress + a CSP allowlist + a new security surface. Revisit when a declared network is allowed. |
| **API access to a remote DB (remote RAG store)** | 2026-08-26 | A `createRemoteRagStore` implementing the SAME `RagStore` interface as `createJsonRagStore` (Unit A §5.3 — the abstraction layer). The document load (traversal) and MCP `rag`/`edit` handlers depend on the `RagStore` interface only, so a remote DB is a drop-in replacement. Requires network egress + auth + a new security surface. Revisit when a declared network is allowed. |
| **RAG object versioning by journal timestamps** | 2026-08-26 | The project journal (Unit A §5.6) already records invertible entries with timestamps. Versioning would reconstruct a RAG object's state at a given journal timestamp (point-in-time snapshot) — e.g. preserve the documentation for a long-term-stable (LTS) build while development continues. Revisit when the project journal lands and a point-in-time reconstruction use case surfaces. |
| **RBAC to selective versions** | 2026-08-26 | Role-based access control to SPECIFIC versions of RAG objects — e.g. test/users have READ-ONLY access to the LTS version, while developers can edit the dev version. Builds on RAG-object versioning (above) + the foundation's security model (tool groups, `security.ts`). Revisit when versioning lands and a multi-role access use case surfaces. |
| **Per-leaf citation from markdown** | 2026-08-26 | The line→node map is COARSE (whole subtree → one RAG object), so per-leaf citation is impossible by design. **ENG-GAP-1 (markdown node-identity preservation) is SHELVED 2026-08-26** — per-leaf citation stays impossible by design. Revisit only if a markdown-as-input flow becomes supported. |
| **Markdown parsing to storage via text-match diffing** | 2026-08-26 | A future feature to ingest markdown (e.g. an external editor's export) back into the RAG store. **Will rely on TEXT-MATCH DIFFING, NOT node-identity comments** — comment IDs are fragile (an external editor could delete/alter them) and markdown is export-only today. Revisit when a markdown-as-input use case surfaces. |
| **Shared-node edit notification + save prompt** | 2026-08-26 | When a user/agent edits a section (RAG node) that is incorporated into MORE THAN ONE document (a CROSS-DOCUMENT-SHARED node, review §13), NOTIFY them that the node is shared across N documents. When the document would save, PROMPT whether the text should be changed for ALL owners (update all duplicates) or whether SOME should be preserved on a CLONE of the original (fork the node for one document, leaving the others unchanged). **Revisit condition MET 2026-08-27 — the editing path (Unit D) has landed** (the cross-document shared-node model is implemented in Unit C; Unit D implements the edit write-back + re-traversal). Still SPECULATIVE — not scheduled; a candidate for a future unit. |
| **Edge/node staleness flagging (bidirectional)** | 2026-08-26 | A staleness-tracking aid for the RAG layer. When an edge's text/content is updated, the connected nodes (its source/target) are FLAGGED for possible staleness — their content may reference the old edge content (e.g. the A→D reference edge's explanation, which a node's text may quote). Likewise, when a node's content is updated, the connected edges are FLAGGED for possible staleness — their content may reference the old node content. The flag is a REVIEW AID only: it does not change the authoritative store, does not block edits, and does not auto-update anything — it surfaces "this connected element may now be inconsistent" for the user/agent to review. Revisit when the editing path (Unit D) lands and edge-contained content (e.g. the A→D reference edge's explanation) is editable. |
| **Document tabs (multi-document simultaneous render)** | 2026-08-26 | The CROSS-DOCUMENT-SHARED duplicates are PER-RENDER materializations; render is transient. In the current single-document view, only ONE document renders at a time, so only ONE instance of a shared subtree exists at any moment (documents cannot loop in one view). The N duplicates COEXIST only if multiple documents render simultaneously — which requires UI TABS. Add document tabs to render several documents at once (then the "update all duplicates" concern becomes live). Revisit when a multi-document view is wanted (the rendering spine, Unit C, has landed). |
