| **DECIDED: RAG-AUTHORITATIVE — the RAG layer is authoritative; the provident graph is a transient render materialization produced by a RAG traversal** | 2026-08-26 | The RAG store (RAG nodes + edges) is the persistent source of truth. The provident graph only exists after compilation by the RAG traversal (a `LegacyInitialData` envelope → `translateLegacy` → `renderProducingProcess`). The graph is a pure projection of the RAG store, maintained in-place for content edits (RAG-store-commit-first, then state-slice the affected element) and full re-traversal for structural edits. Invariant: "the RAG store is always correct; the materialized graph is always re-derivable." The engine's graph-is-authoritative pin holds at the graph→HTML boundary. | user clarification 2026-08-26, `docs/specs/astrographer-review.md` §8.1/§9 |
| **DECIDED: SUBTREE-OWNERSHIP — a RAG object OWNS a subtree of Provident nodes (many-to-one back-reference `Map<ragNodeId, nodeId[]>`)** | 2026-08-26 | A RAG object maps to a subtree (a `contentNodes`-owned content root + its children), NOT a single node. The subtree root can link children and have no family parent, attached into a root-visible zone via placement/component logic. The RAG object's text = the markdown of its whole subtree, embedded as ONE chunk (a `ul` + its `li` children are one RAG object / one embedding). The back-reference is many-to-one, rebuilt per traversal. | user clarification 2026-08-26, `docs/specs/astrographer-review.md` §10 |
| **DECIDED: MARKDOWN-EXPORT-ONLY — markdown is an export-only surface; agent changes go through direct MCP updates** | 2026-08-26 | The `MarkdownAdapter` output is a read/export surface for the agent, NOT an edit surface (the ownership loss from D7 is accepted). Agent-driven changes go through direct MCP `edit`-group mutations to the RAG store, not markdown round-trips. Diffing markdown vs. generated source is a FUTURE SPECULATIVE feature (`docs/pending.md`). | user decision 2026-08-26, `docs/specs/astrographer-review.md` §11 |
| **DECIDED: FORM-CONTROL-EDITING — editing is commit-on-blur via a provident-rendered textarea/input, writing back to the source RAG object** | 2026-08-26 | Editing is a form control (textarea/input) committed on blur via a `state-slice` content replace, then write-back to the source RAG object (via the back-reference). NOT contenteditable (fights graph-is-authoritative; `DomAdapter.text` clobbers a live editor). NOT a zone-targeted state-slice (FS-10 blocks it) — write back to the RAG store → re-traversal. A dirty-edit guard queues (not executes) a rebuild while a control is dirty. Caret/focus is host-side state keyed by RAG node id, restored after rebuild. | user confirmation 2026-08-26, `docs/specs/astrographer-review.md` §3b/§9 |
| **DECIDED: DERIVED-DOC-FLOW — doc-flow edges (doc-head/next-section/doc-end) are authoritative in the RAG store; the traversal maps them to family order + a doc-head marker prop** | 2026-08-26 | The RAG store carries doc-flow edges as authoritative. The traversal realizes them in the engine as family child-anchor order + a doc-head marker prop (no new engine roles — closed `Role` union). The traversal VALIDATES the edges (cycle/missing-node/missing-head) and falls back to family pre-order on violation. | user clarification 2026-08-26, `docs/specs/astrographer-review.md` §3c/§9.2.3 |
| **DECIDED: LEXICAL-FIRST-RETRIEVAL — BM25/tf-idf behind an interface-swappable `Embedder`; graph traversal for context assembly** | 2026-08-26 | Retrieval is lexical-first (deterministic, offline, testable) behind an `Embedder` interface; vector embeddings deferred (Unit F). Selection scores all RAG nodes, takes top-k, then assembles context by graph traversal (bounded). The line→node map is a first-class assembly output (coarse: whole subtree → one RAG object). | `docs/specs/astrographer-review.md` §3d/§9.2.10 |
| **DECIDED: SINGLE-WRITER-STORE — the RAG store is the lock point; the main process owns all writes; MCP and UI both route through it** | 2026-08-26 | A main-process `createJsonRagStore` (module-store pattern) serializes writes through a queue/mutex. MCP `edit` tool handlers and the renderer's commit-on-blur IPC both call the same main-process store methods. No renderer-side writes to the RAG store. This is the concurrency model for MCP↔UI equivalence. | `docs/specs/astrographer-review.md` §9.2.6 |
| **DECIDED: RAG-EDIT-MCP-GROUPS — new read-only `rag` + mutating `edit` MCP tool groups, both default-off, through the five-seam gate** | 2026-08-26 | `rag` (read-only, default-off): `rag.query`, `rag.get_document`, `rag.list_nodes`, `rag.get_edges`, `rag.backlinks`. `edit` (mutating, default-off): `edit.set_content`, `edit.create_node`, `edit.delete_node`, `edit.split_node`, `edit.merge_node`, `edit.set_edge`. Editing is NEVER a `code`-group op. Registered through the five-seam gate (`security.ts` TOOL_GROUPS + `mcp-server.ts` ALL_TOOLS + `shared/types.ts` RpcMethod + renderer switch + MUTATING_METHODS). | `docs/specs/astrographer-review.md` §9.2.7 |
| **DECIDED: MULTI-PARENT-DUPLICATE — a multi-parent RAG node is materialized as duplicate subtrees (distinct content roots sharing the RAG id via the map), respecting SI-1** | 2026-08-26 | The engine's single-parent family model (SI-1) cannot represent a multi-parent RAG node. Duplicate-per-parent (each a distinct provident content root sharing the same RAG object id via the back-reference map) is the only option that respects the engine model. Content edits must update ALL materialized duplicates (state-slice every duplicate), or explicitly accept cross-duplicate staleness until the next structural rebuild. | `docs/specs/astrographer-review.md` §9.2.8 |
| **DECIDED: PROJECT-JOURNAL — undo/redo lives in the RAG store's own project journal, not the engine Supervisor journal** | 2026-08-26 | The engine Supervisor journal dies on rebuild (a re-traversal mints a fresh graph). Undo/redo lives in the RAG store's project journal, which records INVERTIBLE entries for both content and structural ops (undoing a structural edit re-traverses). | `docs/specs/astrographer-review.md` §9.2.1 |
| **DECIDED: ENGINE-GAP-HANDOFF — a missing capability is an engine gap (handoff) iff it cannot be implemented by composing existing engine primitives in host code** | 2026-08-26 | Transient graph, back-reference, and RAG→subtree traversal are all project-specific (compose `translateLegacy`/`loadEnvelope`/`renderProducingProcess`/managed channel/five-seam gate). The ONE engine gap: `MarkdownAdapter` `data-node-id` preservation (D7) → handoff doc, non-blocking (the host-side line→node map covers it). The RAG layer is project-specific, not a foundation feature. | user note 2026-08-26, `docs/specs/astrographer-review.md` §8.3/§9.2.11 |
| **DECIDED: DOC-CHILD — a RAG object can own a subtree that CONTAINS nested subtrees owned by doc-child RAG objects (nested semantic units)** | 2026-08-26 | A nested provident node that is large enough for semantic distinctiveness (e.g. a paragraph-length `li` inside a `ul`) is its own RAG object, a doc-child of the containing RAG object. The `doc-child` edge (`{ type: 'doc-child', parent, child, order }`) expresses HIERARCHICAL nesting, distinct from the linear doc-flow edges (`doc-head`/`next-section`/`doc-end`). A RAG object's `ownedNodeIds` EXCLUDES the nodes owned by its doc-children. The traversal materializes doc-child subtrees at their `order` position within the parent's subtree. A doc-child's text = the markdown of its OWN subtree, embedded as a SEPARATE chunk. | user clarification 2026-08-26, `docs/specs/astrographer-review.md` §12 |
| **DECIDED: SOURCE-SWITCHABLE — the `RagStore` interface is the abstraction layer between the JSON store and the document load** | 2026-08-26 | `RagStore` (§5.4) is the INTERFACE the document load (Unit C traversal) and the MCP `rag`/`edit` handlers depend on — NOT the concrete JSON store. `createJsonRagStore` is the JSON-file implementation; a future `createRemoteRagStore` (pending — `docs/pending.md`) implements the SAME interface. The store is injected (constructor/options), never imported directly by the traversal/handlers, so the source is switchable without changing the document load. | user request 2026-08-26, `docs/specs/unit-a-rag-store.md` §5.3 |
| **DECIDED: STRUCTURAL-ROOT — a RAG object's subtree root can be a STRUCTURAL element type (e.g. `div`), not just a semantic element** | 2026-08-26 | A `div` (and other structural element types) is a valid `RagNodeType` root. It groups semantically-related but syntactically-unstructured text lines into ONE RAG object / one semantic chunk (e.g. a lazy/shorthand note like "S3 Bucket types / General Purpose / Vector / Directory / Table" written as plain lines with no `ul`/`ol` structure). The `div` root's children are the text lines; the whole subtree is one RAG object / one embedding. Same subtree-ownership model as `ul`/`ol` — the structural root is a grouping container. | user clarification 2026-08-26, `docs/specs/astrographer-review.md` §14 |
| **DECIDED: CROSS-DOCUMENT-SHARED — a RAG node can appear in MULTIPLE documents at the same time (shared/transcluded nodes)** | 2026-08-26 | A shared node (e.g. A's spec, called by both Class B and Class C) has MULTIPLE `parent-child` edges (one per document) and is materialized as duplicate subtrees in each document, all sharing the RAG id via the back-reference map. A text change updates all duplicates ("if the text of A changes, so do both documents"). **An edge carries a `documentIds: string[]` field (the document root node ids that OWN/USE the edge) — an edge can have MULTIPLE document owners** (a shared reference/content edge, e.g. the A→D edge, lists both B and C). A `next-section` edge's TARGET differs per document, so those are separate edges each with ONE owner. The traversal assembles each document's flow separately. Cost: a node referenced by N documents is materialized as N duplicate subtrees (the price of respecting SI-1). **Material-state nuance (2026-08-26):** the N duplicates are PER-RENDER materializations; render is transient. In the single-document view only ONE document renders at a time, so only ONE instance of a shared subtree exists at any moment (documents cannot loop in one view). The N duplicates COEXIST only if multiple documents render simultaneously — which requires UI TABS (a pending feature, `docs/pending.md`). | user clarity check 2026-08-26, `docs/specs/astrographer-review.md` §13 |
