### 2.2 THE WRITE — the exact `persist()` step sequence, per carrier, in order

**THE SHAPE IS THE LANDED 3a FIVE-STEP, IN ORDER, ONCE EACH — and it is IDENTICAL on both carriers except that only the operator carrier answers a receipt.**

**Both carriers, `persist()`:**

1. **`mkdirSync(dirname(opts.path), { recursive: true })`** — the directory leg.
2. **write the serialized record to `${opts.path}.tmp`** — `JSON.stringify(current, null, 2)` (both carriers serialize exactly as they do today; **the serialization is NOT changed**).
3. **`fsync(tmp)`** — the tmp file is `fsync`'ed **BEFORE** the rename (the rename is what publishes it).
4. **`renameSync(tmp, opts.path)`** — the atomic replace. **THE LIVE PATH IS NEVER WRITTEN DIRECTLY** (§3 `I-1`).
5. **`fsync(dir)`** — the PARENT DIRECTORY is `fsync`'ed **AFTER** the rename.

**THE ORDER IS THE CONTRACT: `mkdir` → tmp-write → tmp-`fsync` → rename → dir-`fsync`. A write that renames without the tmp `fsync`, or that skips the directory `fsync`, FAILS the rows.** **A DIRECT `writeFileSync(opts.path, …)` ANYWHERE in either carrier's write path is `F-2`** — the OLD plain write is **REPLACED**, never kept beside the new shape.

**The tmp file's fate (both carriers, §3 `I-2`):** (a) a **SUCCESSFUL** write leaves **NO** `${path}.tmp`; (b) a **PRE-EXISTING stale** `${path}.tmp` is **OVERWRITTEN** and **NEVER read as input**; (c) **the boot read reads the REAL path ONLY** — a `${path}.tmp` is **NEVER parsed as the record**, whatever valid-looking bytes it carries.

**The fd discipline (carried from 3a's adversarial `G-14`, adopted here as a shape rule, NOT as a copied figure):** each descriptor opened is **closed on every path** — the tmp fd closed after its `fsync` (including when the `fsync` throws), the dir fd closed after its `fsync`, and any residual fd released by a last-resort guarded sweep so a throwing `closeSync` can never replace the receipt with an escape. **The counts are an OUTCOME of the drive, not an anchor.**

**Per-carrier difference, stated once so it cannot drift:**
- **`operator-settings-store.ts`:** every step is wrapped so that **ANY throw at steps 1–5 answers `{ status: 'refused'; reason: 'write-failed' }`** and **never escapes `set()`** (V-5). **A refusal CLEARS NOTHING, EMITS NOTHING, and leaves the previous file at the live path intact.**
- **`engine-config.ts`:** **the same five steps, the same wrap, the same intact-previous-file rule — and NO receipt** (§2.3 ②): a failure at steps 1–5 answers **nothing to a caller**; its only effect beyond the write's shape is that the carrier **records the conflict on the next successful write** (§2.5 ③) and the in-memory config still applies (V-5).

### 2.3 THE RECEIPT — the reader ruling, determined PER CARRIER

**The gate-1 record §3 rules: the sweep carries a receipt ONLY IF THE RECEIPT HAS A READER; where a carrier has no such channel, the unit MUST SAY SO and MUST NOT MINT A VALUE NO CALLER READS. The spec must answer, per carrier, which disposition applies. TAKEN HERE, WITH THE SURFACE READ:**

**① `src/main/operator-settings-store.ts` — A RECEIPT IS MINTED: `lastWriteReceipt()` IS THE READER.**

- **THE READER IS THE STORE'S OWN PUBLIC MEMBER, ON THE MAINTENANCE SURFACE.** The operator store is constructed at a **reachable site** (`src/main/main.ts`), its own interface is **exported** (`OperatorSettingsStore`), and its `set()` resolves through the store to an **IPC handler whose return IS `set()`'s post-state** — so the persist outcome is observable through a declared store member to every existing caller with **ZERO channel change**.
- **WHY THE MEMBER AND NOT A CHANNEL FIELD (the operator carrier's own drift, named so it is not misread as a deviation):** `src/main/main.ts`'s operator-settings SET handler **does not return `set()`'s own resolution** — it returns a binding it holds from the `set` call, and it **broadcasts the payload to a sink whose type carries `OperatorSettings` alone**. So (a) a channel field would be **STRIPPED before any consumer saw it**, and (b) the channel's payload type is **wider than** the store's return, so naming it as the reader would require an **impossible** widening. **The `lastWriteReceipt()` member reads the SAME answer at the store boundary — the closest point to the sink a reader exists — and is licensed by 3a's own `S-4` precedent, which mints the member ALONGSIDE the channel leg.** **Nothing is re-opened, no frozen shape moves, and no preload byte is touched (`I-9`).**
- **THE HONEST LIMIT, STATED RATHER THAN SMOOTHED:** with `set()`'s return shape frozen (`S6`), a channel-level reader is **structurally unavailable** — which is exactly **3a's own recorded finding**, where every renderer `set()` discards the resolution and a renderer-driven row therefore **cannot** observe the receipt. **The member is a MAIN-REALM observability surface; it is not a toast, not a pane indicator, and not a rendered surface.**
- **The type's home is THIS module** — `OperatorSettingsWriteReceipt`, **self-contained, EXPORTED, NO import** — so a **DUPLICATE-HOME** limb can be asserted (the identifier is declared in **EXACTLY ONE** of `src/main/operator-settings-store.ts` and `src/main/security-store.ts`; a declaration in **BOTH** reddens it).

**② `src/main/engine-config.ts` — NO RECEIPT IS MINTED: THE READER DOES NOT EXIST, AND THAT IS RECORDED AS A DISPOSITION, NOT AS AN OMISSION.**

### 2.5 THE READ-PATH DISTINGUISHABILITY REQUIREMENT (the defect's SECOND HALF, discharged)

**THE REQUIREMENT, stated as a property:** **A TORN FILE MUST NOT BE INDISTINGUISHABLE FROM A FRESH INSTALL.** Today both answer `defaultSettings()`/`{engineBaseUrl:null}` through the same `catch`, with **no receipt, no `corrupt` flag and no log line** — so a later `set` from any consumer **overwrites the torn file with the defaults, making the loss permanent**.

**① THE AS-FILED OVERSTATEMENT, KEPT VISIBLE (never deleted — `RCA-8(c)` annotate-beside).** The three gate-1 reviews that recommended the predecessor unit claimed: *"a torn write silently resets the operator's layout/tabs/theme"* — **i.e. all nine fields revert.**

**② THE CORRECTED READING, BESIDE IT — this is the OPERATIVE one.** `sanitize()` is **TOTAL and FIELD-WISE fail-soft**, so **a torn-but-PARSABLE file resets ONLY the fields whose bytes were lost**. **THE ACCURATE SYMPTOM IS: *"an ARBITRARY SUBSET of the fields reverts to first-run, silently, with no receipt"* — smaller in blast radius, worse to diagnose than the reviews claimed.** **A zero-byte or unbalanced-prefix file DOES fail `JSON.parse` and DOES reset all nine — the overstatement is TRUE for that sub-case and FALSE as the general claim.** **Both prints are carried; the corrected one governs.**

**③ THE EXACT DISAMBIGUATION, PER CARRIER (the ONLY distinguishing signals this unit mints):**

- **The absence case** is exactly **`existsSync(path) === false`** at the store's construction.
- **The unparsable case** is exactly **`existsSync(path) === true` AND the parse/`sanitize` leg throws**.
- **`src/main/operator-settings-store.ts`:** the NEW member **`lastReadWasCorrupt(): boolean`** — `true` **iff** the unparsable case was taken. **The two cases therefore differ at the store boundary, and a caller can tell them apart.**
- **`src/main/engine-config.ts`:** the distinguishability is **PERSISTED INTO THE FILE** — the record this carrier writes carries an explicit **conflict marker** once a corrupt read has occurred, so the fact survives the process and is readable by main at the next boot **without a member no caller would read** (§2.3 ②).

**④ WHAT THIS IS NOT (each a finding if claimed):** it is **NOT** a corrupt-file recovery facility (no repair, no backup, no restore); **NOT** a torn-but-parsable detector (a file whose JSON parses is **NOT** detectable as torn at this layer at all — **DISCLOSED**, and it is the honest limit of the per-field reading); **NOT** a rendered surface; **NOT** a new throw; and **NOT** a change to `get()`'s totality (`S8`, §4 m-7/m-8).

**⑤ THE COMPLEMENTARY HALF — WHY THE SHAPE PREVENTS THE TORN FILE IN THE FIRST PLACE.** The atomic five-step is why a torn LIVE file should not arise from THIS carrier again: the rename is atomic on one filesystem, so the live path is either the old record or the new one. **NO DURABILITY CLAIM: this is a SHAPE argument, not a measured outcome.** The distinguishability requirement covers the files that are ALREADY torn (a legacy file, an external writer, a pre-landing casualty) and the OS-level cases the shape argument does not reach.
