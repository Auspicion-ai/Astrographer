## §0 — WHY THIS UNIT IS NOT THE ONE THE PLAN NAMED (the rename, and the blocking it answers)

**THE PROGRAM PLAN NAMED `U-OPERATOR-SETTINGS-REHOME`, AND ITS GATE 1 BLOCKED IT — `BLOCKED-ON-SEMANTICS` FROM BOTH THE VALIDITY AND THE CRITIQUE REVIEWS, EACH REACHING ITS VERDICT INDEPENDENTLY.** The blocking finding is that **the unit's NAME and its AUTHORIZING SENTENCE describe two different units**, and the plan's own unlock clause (*"it consumes the carrier"*) asserts one of them while its parenthetical describes the other's artifact inventory:

- **READING (A) — "re-home" = MOVE the nine-field payload onto the landed tier-1 carrier (`provident-settings.json`).** Under (A): the carrier is keyed by `file.*` reference spellings and gated on `schemaVersion` (`src/main/main.ts` `readStoreCarrier`/`projectAndWrite` refuse a key that does not start `file.` with `'malformed-payload'`), while today's payload is a **flat nine-member JSON object** — so the payload **cannot be written to that carrier as-is**; the unit would have to invent a spelling map for all nine fields, **authorized nowhere**; it would collide with **`file.settings.theme.token`** and **`file.settings.pane.<id>.size`**, which the plan assigns to **`U-STORE-MODULES-ADOPT`** and **`U-STORE-PANE-DRAG-ADOPT`**; and it is **DENIED BY NAME BY A LANDED SPEC** — `docs/specs/unit-store-persist-adopt.md` `§1.2 R-5`/`§3 F-11` deny the operator-settings re-home, and `tests/pd-store-persist-adopt.test.ts`'s `deniedMigrationProblems()` **asserts the file carries no carrier token** (a GREEN-ON-ARRIVAL guard that REDDENS on the re-home landing).
- **READING (B) — the same file merely gains an atomic write discipline.** Under (B) the unit is **a copy of a fork idiom already landed four to six times in this tree** (`src/main/module-store.ts`, `template-store.ts`, `rag-store.ts`, `rag-store-registry-write.ts`, plus unit 2's `atomicWriteStoreCarrier` in `src/main/main.ts` and 3a's `security-store.ts`), it **does not consume the carrier at all**, and its own name is a **misnomer** that would mislead every downstream reader into writing a migration spec for a payload that never moves.

**A spec cannot resolve a contradiction between a landed spec and the plan sentence that authorizes it** — which is why the verdict was `BLOCKED-ON-SEMANTICS` and not `APPROVE-WITH-CONDITIONS`. **THE ARCHITECT'S RULING (`2026-10-04`, recorded here): the atomicity work is chartered, under a TRUE name, as ONE SWEEP over BOTH remaining clause-(1) carriers.** The re-home reading (A) is **NOT** chartered and is **NOT** silently dropped: it is named here, blocked on its own terms, and left to whichever unit is first authorized to mint the nine-field spelling map.

## §2 — THE HAZARD, VERIFIED, AND ITS PROBABILITY (the honesty correction the reviews made to each other)

**THE HAZARD IS REAL AND ITS SYMPTOM IS STATED MORE PRECISELY BY THE CRITIQUE THAN BY THE REVIEWS IT CORRECTED.** The claim inherited from the recommending reviews was *"a torn write silently resets the operator's layout/tabs/theme"* — i.e. **all nine** fields. The critique traced the read path further and found the claim **overstated in blast radius and understated in diagnosability**:

- The read path is `existsSync` → `readFileSync` → `JSON.parse` → `sanitize(...)` inside a `try` whose `catch` answers **`defaultSettings()`**.
- `writeFileSync` opens the live path with the **truncating** flag, so a death between the truncate and the write's completion leaves either **zero bytes** or a **prefix** of the serialized object.
- **A zero-byte or unbalanced-prefix file FAILS `JSON.parse` and therefore resets ALL nine fields** — the recommending reviews' case.
- **BUT a torn-but-PARSABLE file is the more insidious case**: `sanitize()` is **TOTAL and FIELD-WISE fail-soft**, so a partial record that still parses resets **only the fields whose bytes were lost**, defaulting the rest. **THE ACCURATE SYMPTOM IS THEREFORE: "an ARBITRARY SUBSET of the fields reverts to first-run, silently, with no receipt" — worse to diagnose, smaller in blast radius** than the reviews claimed.
- **AND THE DEFECT HAS A SECOND HALF NEITHER REVIEW NAMED AS SUCH:** because the read path's `catch` is **observationally identical to the legitimate first-run path** (`existsSync` false → `defaultSettings()`), **a torn write is INDISTINGUISHABLE from a fresh install at every downstream surface** — no receipt, no `corrupt` flag, no log line. A later `set` from any consumer then **overwrites the torn file with the defaults, making the loss permanent.**

**THE PROBABILITY IS LOW AND THE CLASS IS COMMON — STATED SO THE UNIT IS NOT OVER-SOLD.** The window is one `writeFileSync` of a small JSON object (sub-millisecond), reached only on operator-initiated settings writes — **not** on a per-document, per-edit, per-query or per-frame path. And the module store carries the same **kind** of gap. **The honest ruling: the difference between this sweep and the deferred module-store work is one of COST and CHEAPNESS, not of KIND** — this sweep is the **smallest remaining instance of the class, not the worst** — and the unit is justified by **the clause's own quantifier** (*every* carrier), not by a severity claim this record does not make.

## §3 — WHAT THE SWEEP ADOPTS, AND THE TWO PRECEDENTS IT REJECTS BY NAME

**THE SHAPE IS THE LANDED `3a` FIVE-STEP, IN ORDER, ONCE EACH: `mkdirSync(dirname, { recursive: true })` → `${path}.tmp` write → `fsync(tmp)` → `renameSync(tmp, path)` → `fsync(dir)`,** with the live path **never** written directly, and **no `${path}.tmp` surviving a success** (a stale tmp is overwritten and **never parsed**).

**THE TWO REJECTED PRECEDENTS, EACH WITH ITS REASON (the spec must carry this table):**
- **REJECTED BY NAME — `src/main/module-store.ts`'s `persist()` (tmp + `renameSync`, NO `fsync`).** Rejected because it is the **very gap this sweep exists to close**: a two-step tmp+rename prevents a torn *file* but not a lost *rename*, and adopting it would make the sweep's own subject the sweep's own shape.
- **REJECTED BY NAME — `src/main/main.ts`'s `atomicWriteStoreCarrier(path, serialized)` (the same five steps, no façade seam, a `boolean`).** Rejected **only** as the *unit's own* shape, not as a precedent: it has **no injected façade**, so a register driving it could assert only that a write happened, **not its call order and count** — and the honesty discipline requires the atomic claim to be **shape-asserted over an injectable seam**. (It remains correct for its own caller.)

**THE FAÇADE AND THE RECEIPT — ONE RULING, TAKEN HERE BECAUSE THE REVIEWS LEFT IT OPEN.** The unit adopts **3a's injected `fs?` façade** (ADDITIVE-OPTIONAL; absent ⇒ the real `node:fs`; the seam is INERT by default) because **the façade is what makes every claim falsifiable in `[T]`**, and it adopts **a receipt** — but **ONLY IF THE RECEIPT HAS A READER.** `3a`'s receipt is not decoration: it rides the **IPC response** and its rationale is *"a persist failure the caller cannot observe is a finding"* — it **replaced a swallow**, which is exactly this unit's defect. **The ruling: the sweep carries a receipt on a channel a caller actually reads**; and where a carrier has **no such channel** (`engine-config.ts` is read/written within main for base-URL resolution and has no IPC response of its own), the unit **must say so and must not mint a value no caller reads** — a receipt with no reader is scope creep and would be its own finding. **The spec must answer, per carrier, WHICH of the two dispositions applies.**

**THE SWALLOW: REMOVED, NOT RETAINED — WITH ONE NAMED EXCEPTION.** `3a`'s disposition removed the plain write **and** replaced the swallow. This sweep follows it, **except** that the operator store's *"a settings write must never crash the app"* posture is **LOAD-BEARING AND IS RETAINED AS A POSTURE, NEVER AS A SILENT ONE**: the write's failure must be **observable** (the receipt) while still **non-fatal** (no throw into the settings path). **The empty `catch {}` as a SILENT absorber is removed; the non-fatal posture is kept and made visible.** For `engine-config.ts` the same ruling applies on its own terms.

## §5 — THE LAYER AND THE LIVE LEG (RUN, NOT PARKED)

**`[T]` constructed store / `[H]` byte-scan.** **THE LIVE LEG RUNS.** The reasons a park was legal for `3a`/3b are **ABSENT HERE**:
- **`RCA-11` clause (b)** permits a park only for a **structurally non-exercisable** surface (an OS-owned dialog, or a scope the MCP+CDP surface cannot reach). A settings file written by a reachable store is **not** such a surface.
- **The seam EXISTS and is PROVEN.** `src/main/main.ts`'s `userDataFromArgs` **is** the `--provident-user-data=` seam, landed by unit 2, whose live battery **RAN** `L-1..L-4` including a **REAL app-restart round-trip**. **The program plan's excuse that the fork has no such seam is STALE at this head**, and no park may be justified by it.
- **THE WITNESS OBLIGATION IS THE UNIT'S OWN SUBJECT.** `docs/defects.md`'s row records that **our own legs must witness our own files** (a fork's file is outside every foundation witness), and `3a`'s own note records that the obligation **stays OPEN precisely because that unit took no live reading of its own file**. A unit whose entire justification is a **file's write shape** may not park the only reading that would witness that file.
- **THE RUN MUST BE AN ORDER CLAIM, NEVER A TIMING FIGURE:** write → restart → the value observed in the carrier — **no latency, no durability, no crash-window figure.** The row's own honesty rule forbids the rest (`RCA-12`).
