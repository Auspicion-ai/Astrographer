## 1. The program, as ruled (not re-opened)

- **The baseline is the completed port** (D-25): this is an **incremental re-plumbing on the fork's own chrome**, never a base swap, and the live gate keeps reading throughout.
- **D-23 fixes the record's PAYLOAD**: display state — the document a tab showed, the caret, the scroll position / visible section — and **never document content**. It is a STATE SEAM, not a data migration.
- **D-24 fixes the panes' BEHAVIOUR**: they keep their INTERNAL DATA CONTENT and take the foundation's relocation/display/styling and EVENT-DRIVEN update model — a component that learns something **fires a listener for the owning pane's renderer, or writes the store record**, and the pane updates because it HEARD.
- **D-8 stands for every unit**: "event-driven" means a listener or a record write drives the graph. The paint is provident data through the managed channel; hand-written DOM is a review finding at any layer.
- **D-9/D-11 stand**: no unit edits `node_modules/`, the upstream package source or `../Provident-Electron/`. A foundation gap is **catalogued** (`docs/L1/foundation-features-findings.md`), never patched and never re-authored as a vendored copy (ASM-2).
- **The measured starting point, `READ` at this head:** the fork has **zero** `storeroom` references in `src/**`, **no** record-family module (`view-record`/`tabs-record`), and **none** of the foundation's four change pushes (`IPC_VIEW_CHANGED`/`IPC_TABS_CHANGED`/`IPC_MODULE_CHANGED`/`IPC_SECURITY_CHANGED` — `grep` over `src/**` returns nothing; the foundation's 11 bridge channels are counted at `strata/records/foundation-import-second-build-critique-2026-11-16.md:11`). **So D-24's record arm has no subject at this head**, and `B-1` builds one.
- **What the migration replaces, `READ`:** every pane change is answered by RE-ASSEMBLY. `SidebarPanes.refresh()` re-loads the app-graph envelope and rebuilds the operator envelope (`src/renderer/sidebar-panes.ts:2457-2485`), and both gnosis hosts call it on every settle (`src/renderer/renderer.ts:1617-1619`, `:1633-1635`); the operator-settings path re-derives the WHOLE graph and not only the envelope — `onOperatorSettingsChanged` ends at `requestRebuild('operator')` (`src/renderer/sidebar-panes.ts:2858-2868`), which its own comment names *"a FRESH traversal — never `refresh()` over the cached envelope"* (`:2854-2856`). The pane registry's only change channel is an **enabled-state** one (`src/renderer/pane-registry.ts:59-74`), and `PaneContext` is handed in **at re-assembly** (`:17-40`).
- **The precedent that prices the invariant:** `reveal-without-reassembly` landed `INV-R` — *no reveal transition may be applied by a re-assembly*, measured as `0 setLayout` / `0 loadEnvelope` / `0 loadAppGraph` (`docs/L2/shell-chrome/reveal-without-reassembly.md` §2, §4.1). **`B-3` adopts that measurement SHAPE** — a named invariant whose evidence is counted zeroes on the host — with **its own three counters** (`0 loadAppGraph`, `0 mountOperator`, `0 refresh()`; INV-R's are `0 setLayout`, `0 loadEnvelope`, `0 loadAppGraph`), and the difference is deliberate: a pane update must not re-assemble the tree, while a reveal must not touch the record either (`ASM-B-5`).
- **The engine's push channel EXISTS and is landed** — `GET /changes`, the SSE change feed (`../Gnosis/src/bin/gnosis_server.rs:1056`, handler `:952-1040`; engine-side landing `RECORDED` `docs/specs/post-division-engine-offload-inventory.md:222` "GR-5 … LANDED as `U4`"). **No new engine channel is requested**; `B-4` consumes it. Its one measured residual is ASM-B-4.

## 7. What no unit may do

- **Write document content — or a second document ref — into the record** (D-23). A design that does is refused by the ruling it implements.
- **Hand-write DOM**, in the paint or anywhere else (D-8): every pane element is envelope data at its authoring site.
- **Widen a package or the foundation tree** (D-9) — `provident-ssr`, `provident-storeroom`, `provident-editable` and the adjacent `../Provident-Electron` are read-only, and a gap is a finding.
- **Apply a pane update by re-assembly** once its unit has landed (`INV-E`) — the counter is the evidence, not the intention.
- **Claim an app-green reading from a node green** (D-10, RCA-12), or cite `SKIPPED-BY-RULING` as coverage.
- **Let one unit carry a sibling's behaviour**: every pane family is its own unit because RCA-2 says a multi-unit deliverable is split per unit before any unit starts.

## 8. Assumptions this design takes (each with the alternative it rejected)

- **`ASM-B-1`** — the seam is **ported by hand** into the fork, not vendored: the foundation's record modules are `src/main` modules, and D-13's measured rule is that the fork's equivalents are its own code (the foundation's `renderer.ts` 7,844 lines vs the fork's **1,722** at this head — `READ`, not D-13's 1,601, which is a 2026-11-15 reading). Rejected: adding `view-record`/`tabs-record` to the fifteen-module vendor set, which would need a lock move and would make the fork's copy a second source of truth (ASM-2).
- **`ASM-B-2`** — the family carries **no document ref**: the tab's target is already carried by `OperatorSettings.tabs.open[].target` (`READ` `src/shared/types.ts:787-790`, `src/renderer/tab-state.ts:33-38`), the tab's display state is NOT persisted there today (`grep` finds no caret/scroll member), and a second carrier for one persisted fact is the adjudication D-15 refused. Rejected: making the family the sole carrier of the target, which is a `tab-strip` migration D-23 did not ask for. **L0 may overrule this cheaply now and expensively later** — D-23's wording does name "the document it showed".
- **`ASM-B-3`** — the family is `file`-tier (it must survive a restart, D-23's "reconstruct") with a **pinned write event set**, not a per-keystroke stream (D-23's own cost). Rejected: `mem`-tier, which cannot reconstruct anything after a restart.
- **`ASM-B-4`** — the engine feed's consumer **re-reads on connect** and never treats the feed as gap-proof: the route accepts **no request-side cursor** (`READ` `../Gnosis/src/bin/gnosis_server.rs:968-976`), so a subscriber that reconnects cannot distinguish "nothing happened" from "a window rolled past me". Rejected: filing a new engine request — GR-5/`GRQ-10`/`GRQ-11` already carry the route and its restart semantics (`docs/feature-requests/gnosis-engine-prerequisites.md:232-262`), and a request that duplicated a landed route would be the corpus's own "request document is not a status source" failure.
- **`ASM-B-5`** — **`INV-E`'s counters are the pane update's own, not `INV-R`'s.** A reveal must not touch the record (`0 setLayout`/`0 loadEnvelope`/`0 loadAppGraph`); a pane update must not re-assemble the tree (`0 loadAppGraph`/`0 mountOperator`/`0 refresh()`), and it MAY write the record, because D-24's record arm does exactly that. Rejected: copying `INV-R`'s three counters verbatim, which would make the invariant unfalsifiable for a pane whose update legitimately rests on a delivery.
