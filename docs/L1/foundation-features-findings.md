## 1. The findings

**Path convention in this section:** an unprefixed `src/…`, `docs/guides/…` or `package.json` path is the **foundation's** (`../Provident-Electron/…`); `node_modules/…` is the **fork's own install**; a fork source path is named `fork …`. §2 names its own.

### `F-1` — the delivery's fan-out cannot scope a subscriber to a family (`READ`)
- **Symptom.** `ViewDelivery.subscribe(handler: () => void)` takes **no argument**, and the fan-out calls `handler()` with nothing (`READ` `src/main/view-record/index.ts:1416-1418`, `:1442-1452`), while the app's sink is handed the **address** on the same delivery (`:1451`). The contract is stated as *"a committed change of any of the four roots calls `handler` once"* (`READ` `docs/L3/view-record/delivery.md:30`) — so it is deliberate, not a defect, and the foundation's own app has exactly ONE destination (`READ` `view-record/index.ts:1432-1433`).
- **Why it is a gap for a fork.** D-24's model is **per-pane** ("fire a listener for the backlink pane renderer"). With one address-less fan-out, a fork's N panes must each re-read the whole shape and diff it, or subscribe N times and repaint all N — the re-assembly the migration exists to delete, moved one layer down.
- **Why §8 does not cover it.** §8 is about record WRITES; the delivery's own shape is not among the seven refusals, and §10 assigns the fork its pane names but not the subscription's arity.
- **Disposition:** **a request doc** — `DLV-1` (`docs/feature-requests/provident-electron-record-delivery-requests.md`), because a subscription's arity is a MECHANISM (`docs/FORKER.md`'s mechanism/app split).

### `F-2` — no documented extension contract for a fork that needs its OWN record family (`READ`)
- **Symptom.** The foundation's four view roots are a closed module-private array (`READ` `src/main/view-record/index.ts:1395-1400`), `viewDeclaredRoots()` is the module's own (`:1334-1341`), and the placeholder set is closed by §8.3. **The mechanism a fork needs DOES exist** — the boot builds its crossings' entries and spreads them into ONE construction (`READ` `src/main/main.ts:437`, `:445-452`), and the seam takes both lists from the caller (`READ` `src/main/storeroom.ts:97-126`) — but **`forking.md` never states it**, in any section.
- **The second half, which the guide does not mention at all:** a family appears in **two** lists and they are not the same list — `viewDeclaredRoots()` publishes **four** (`:1334-1341`) while the batch declares **three**, the fourth being "a root no pair holds" (`READ` `src/main/data/types.ts:180-182`, foundation `D-145`). A fork that declares one list and not the other gets either an unguarded address or a family whose writes never deliver.
- **Why §8 does not cover it.** §8.3 answers "the *placeholder* export you guessed does not exist"; it does not answer "what must a fork write to add a family". §10 lists the fork's half as names/figures, not as a family.
- **Disposition:** **a request doc** — `DLV-2` (a documented extension contract; a guide section plus a stated shape).

### `F-3` — the seam's declared-surface census is not re-measured at the version the foundation itself declares (`READ`, one limb `UNSOURCED`)
- **Symptom.** `src/main/storeroom.ts:22-38` states its census **measured at `provident-storeroom@1.9.3`** with a `1.10.0` note (15 string members; **13** own symbols at construction), while the foundation's own `package.json:28` declares `^1.11.0` and its boot reasons about 1.11.0's **four registration instants** (`READ` `src/main/main.ts:440`).- **What is and is not falsified.** At the installed 1.11.0 (`READ` `node_modules/provident-storeroom/package.json:3`) the declared member set is the same **15** (`READ` `node_modules/provident-storeroom/index.d.ts:1032-1417`, `StoreInstance` whole), so the member count is **not** falsified. The **13-symbol count is `UNSOURCED` at 1.11.0** — this pass cannot construct an instance.
- **Why §8 does not cover it.** §8 is behavioural; a census drift in a docblock is not a refusal a fork meets by writing code.
- **Disposition:** **a `docs/defects.md` row** (L0 files it): *the foundation's seam census names a version it no longer declares; the member list is unchanged at 1.11.0 and the symbol count is unverified there.* The fork's own seam (`B-1`) re-measures at its own install and cites its own reading, never this one.

### `F-4` — no documented route by which a data source that is NOT the record reaches a pane (`READ`)
- **Symptom.** The guide's complete list of lawful runtime-content routes is **three**, and all three are graph or record writes: *"A record write … A graph write on the node itself … A `rows-mint`"* (`READ` `docs/guides/forking.md:189-199`). The foundation's own deliveries bind **profile-store addresses only** (`READ` `src/main/view-record/index.ts:1395-1400`), and the graph *"is not a store"* by the foundation's own ruling (`READ` `src/renderer/view-client.ts:3-20`).
- **Why it is a gap for a fork.** The fork's pane data — backlinks, doc-heads, query results, the engine's health and CRUD — lives in a RAG store and an HTTP engine, **neither of which is a record family**; and D-23 forbids putting content in the record. So a fork must author its own change channel with none of the foundation's guarantees (address-only push, delivery at construction, re-read inside the listener) stated for a non-store source anywhere.
- **Why §8 does not cover it.** §8 answers "what refuses you"; this is "what the guide never describes". §3.1 is the closest section and it stops at the store/graph boundary.
- **Disposition:** **a request doc** — `DLV-3` (a documented delivery shape for a non-record source; P2, since the fork can author the channel itself and loses only the shared discipline).

### `F-5` — the creation-instant delivery, and the dropped-push trap it sets, is stated in code only (`READ`)
- **Symptom.** A delivery fires at the store's **construction**, before any window exists, so `BrowserWindow.getAllWindows()` is empty and a bare `webContents.send` is discarded; the foundation's answer is a per-channel held-then-flushed queue — `createDeliveryQueue`'s body at `src/main/main.ts:173-197` (`held`, `arm()`, the unconditional clear) and `createPendingChange`'s pending set at `:230-251`, constructed beside the two push loops at `:266-334` (`READ`; the docblocks there record the measurement as `D-218`/`D-222`, and `:983` states *"the two pushes' consumers are the realm's own listeners"*).
- **Why it is a gap for a fork.** Every fork that adds a channel copies this queue or silently loses its first delivery — the exact defect the foundation itself once had (*"the empty array this line replaces was the whole defect"*, `READ` `:438-443`). `forking.md` §8's seven refusals do not mention it and no section states the queue's shape.
- **Disposition:** **a request doc clause** — folded into `DLV-2` (the extension contract must state the pre-window hold), not a separate item.

**Count: 5 findings — 4 mechanism/documentation gaps that owe request items (`F-1`→`DLV-1`, `F-2`→`DLV-2`, `F-4`→`DLV-3`, `F-5`→`DLV-2` clause 3) and 1 defect row (`F-3`).**
**The priority, stated so it is not over-read:** **none of the four blocks a unit of the migration program** — that program ports the seam by hand (`ASM-B-1`), so it needs none of them. They block the route `strata/pending.md` row 1 still holds open (adopting the foundation's record families wholesale) and every other fork that adds a pane family today (`docs/feature-requests/provident-electron-record-delivery-requests.md`'s own opening says the same).
